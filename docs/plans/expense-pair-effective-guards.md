# 同一笔消费关联：有效统计与旧写入保护（R16，未开放入口）

依赖：[私有确认/撤回事务核心](expense-pair-private-lifecycle.md)、[schema5 持久化基础](expense-pair-schema5-foundation.md)。分支仍基于 PR14/schema4 链，草稿 PR，不合并、不部署。

## 本片范围

- 有效统计：`Dashboard` 在单一读事务内完成授权、账本版本、月份、明细与关联加载。active 决策的 secondary 整条从总额、分类、条数、搜索和分页中排除，primary 保留；撤回后两条原始记录恢复计入。原交易、来源、分录、指纹和 `source_records` 一律不改。
- 失败关闭：关联元数据损坏、成员事实漂移或结构不完整时，Dashboard 返回 `expense_pair_unavailable`，不回退到重复计算的原始总额。schema4（迁移前）无关联表时按无关联处理。
- 旧写保护（同一事务、授权之后）：交易为 active 成员时，`Annotate`、`PreviewCorrection`、`Correct`、`CreateRefund` 返回 `expense_pair_locked`，零写入；导入 `Commit` 的重复分支会给成员新增来源链接，同样拒绝整批；导入撤销/恢复中只要批次含 active 成员，预览标为阻塞，执行时整批拒绝。
- 不受影响：`Create`、`CreateTransfer` 可继续新增，新交易不会自动并入关联；导入历史、来源详情等证据视图保持原始数据。
- 客户端：导入撤销面板阻塞提示改为对撤销/恢复都正确的通用文案。

## 仍未完成（门禁保留原因）

- 正常 `Open` 对非空关联表仍拒绝打开；尚无 HTTP/UI 确认与撤回入口，也没有独占升级流程。
- `Refunds` 仍是原始交易级摘要，不映射到关联主记录，也未做严格关联检查；需在开放入口前明确策略并补测试。当前有效关联禁止已有退款，两成员新增退款均被拒绝，因此这不构成已证明的重复退款漏洞。
- 待核实队列和来源历史是原始证据视图，不因统计去重而删减；导入疑似重复只提示存在相似交易，不汇总有效金额。
- 已补 secondary 专属搜索、整页边界、撤回恢复搜索，以及独立连接读与确认/撤回竞发的完整快照断言（重复 race 10 次通过）；该并发测试不保证每次调度都实际重叠，也不证明旧写与确认的所有并发交错。
- 已直接覆盖纯净 schema4 零表允许、同名视图/孤立审计残留拒绝、schema5/未来版本零表拒绝。
- 未做正常双端关联验收；当前正常环境 Dashboard 仍为原始统计。
