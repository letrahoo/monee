# M11 S3：同一支出事件决策合同（推荐草案）

## 状态与基线

**这是可执行设计与待决清单，不是财务功能实现，也不是已批准的产品取舍。** 本分支仅文档，独立来自已合并main `72f2a37`。PR18 `c161fb5` 的只读提示/客户端、PR17来源冻结、PR14转账/schema4均未合并；引用它们说明技术边界，不隐式引入生产依赖，不执行迁移或部署。

M11目标仍是只计一次、保留证据、误关联可纠正、覆盖旧迁移重叠。现有同日/类型/金额/币种/商户与不同Source展示名只提供排查线索。**即使只有一个候选，也不证明同一经济事件、原始普通消费或资金账户身份。** 本合同不能把只读响应、ledgerVersion或未来preview当作确认许可。

## 2. 方案选择与推荐

| 方案 | 结果 | 建议 |
| --- | --- | --- |
| 软删“重复”交易，或重指source_records到赢家 | 改变导入undo所有权，容易丢来源/复活错误记录，原ID与审计含义改变 | 不采用 |
| 仅往change_log写关联JSON，再让一个报表少算 | 其他读写与旧二进制忽略事件而双计；零DDL并不等于兼容 | 不作为上线捷径 |
| 新增平衡的冲销/补偿分录 | 原记录可保留，但补偿的类型、计数、日期、资金账户、撤回及所有报表仍须完整定义 | 可选；不能先当income/refund伪装冲销 |
| 类型化定向pair决策(primary/secondary)+成员+修订，并统一effective transactions/postings | 原来源/交易/分录保留；由用户明确会计代表，成本是所有正式读取与旧写入口都要协调 | **推荐受限双成员v1进入评审**，不是通用多成员经济事件模型，也不代表已批准或可立即编码 |

推荐模型的概念实体是ledger范围内的decision/group、member、append-only revision和版本化evidence refs。每个活动成员至多属于一个活动组，复合ledger外键禁止跨账本。首个写切片建议仅两条尚未分组交易，无嵌套、传递合并、组间union或自动第三成员吸收；实际表与迁移编号在门槛D1解决后另定。

## 4. 推荐的有效财务投影

1. 原transactions的财务字段、postings、imports、source_records及其原ID/identity/fingerprint/normalized_json/preview保持原事实，不重写到“赢家”；来源字节与原规范化快照也不变。成员metadata版本是否递增由D8明确，不能悄悄更改或倒退。
2. 正式财务入口统一解析effective event：独立交易贡献一条；活动两成员组按明确会计代表贡献一次。**effective postings必须与同一选择对应**，每个事件选择代表的完整两条posting，另一成员两条都不参与有效财务且不物理删除，分录仍平衡，不能费用一份、资金两份。若架构仍定义raw posting之和就是最终账簿余额，overlay不能宣称兼容，须先明确调整权威定义或选择完整调整分录方案。
3. 原始记录数、来源出现次数、来源显示名数与经济事件数分开命名。来源覆盖可保留两个来源，但不等于两次消费；不得把所有SourceCount改成事件数。
4. 月份集合、收入/消费毛额/退款/净额、分类、正式列表、搜索/分页/总数及未来年度/导出/余额/变更消费都必须从同一有效投影取得；来源/审计查询则明确展示原始成员及决策修订，不将原记录藏到无法追溯。
5. 同一事件多成员的分类/来源搜索到底按代表还是任一成员命中、事件展开/分页如何表达，属于D3/D6，实施前必须选定。不能“总数1、明细两笔都像正式消费”而不解释。
6. 不破坏原identity去重，也不因新sourceConfigId生成新hash/identity来补造交易。新来源到达同一原交易时保留新occurrence，但不自动变成当初已批准的证据或新组成员；先显示独立待评估证据。
7. 已持久化decision/member/revision自身也须可验证：未知payload/schema版本、缺成员或代表、重复active membership、跨ledger/循环/版本不一致等禁止退回raw两笔、忽略坏组或任选代表。受影响账本的正式财务读取应明确unavailable，不返回0或可误用合计；相关预览/confirm/withdraw冲突且零写。原始证据可按原权限用于诊断，恢复只能通过明确repair/migration或匹配有效快照，不能静默删除关系。SQL integrity/foreign_key_check不替代这些应用级检查。

## 5. 独立的预览、确认及撤回合同

以下名称仅是建议操作名，**没有注册API、发布OpenAPI或实现端点**。

### PreviewSameEvent

当前准入+ledger owner/editor的写资格先验证，再在一个一致快照读ledger/group/member版本、原始证据、当前交易和分录、全部相关依赖。候选仅是输入ID来源，服务器重新计算资格和影响，不信任hint的actions/版本或客户端金额。

输出应包含：明确的人工声明、两条成员与所选会计代表、证据完整/缺失/未知状态、逐期间/分类/分录/计数前后影响、会被阻断的相关操作及绑定输入摘要。摘要是私有并发校验材料，不是脱敏、身份或授权证明；不向模型发送原文/普通哈希。预览本身不改变正式账务，是否保存短期预览另定，不得顺手递增财务版本。

### ConfirmSameEvent

一个写事务内按顺序：当前准入/成员写资格 → 解析规范请求并计算绑定ledger/actor/action的完整canonical request hash → 读取同scope/key幂等记录并比较hash（异body409；仅同hash返回原成功收据及当前决策状态，不执行新财务写） → 无既有结果的新操作才fresh资格、证据/分录/依赖及已知版本重算 → 与预览绑定内容完全一致 → ledger+两个成员+group/decision版本CAS → 保存决策/修订/关系及审计、幂等结果 → ledger版本递增一次 → commit。原事实不变，只产生已定义的有效投影变化。

成功key重放前仍必须授权；同key异body冲突，其他用户/操作不能捡取成功结果。未知结果重试保留原body/key，不以超时生成新请求。对缺失/跨账本对象在完成当前账本授权后404；不支持/特殊输入422；数据或依赖漂移409。幂等记录、审计和投影必须同事务，不能先写关系后补日志。

### WithdrawSameEvent

只撤回本decision拥有的有效等价关系，不修改或复活原交易。重新验证当前权限、decision/group/ledger/member版本、原证据与活动依赖；不能把“有两条原记录”解释成无条件加回一笔。若成员被其他操作修改/删除、产生退款或批次状态改变，返回冲突并给可理解的后续处理，不擅自恢复别的操作拥有的数据。

在D5首写“关联期间禁止成员变化”的推荐下，正常撤回应恢复关联前同两条独立财务投影；不承诺恢复旧表单/原批自动Undo资格（D8）。历史决策/evidence refs仍保留，不能擦审计。重复撤回可幂等确认已撤回，不重复增加总额。再次确认用新的决策修订/版本/操作key，旧确认key不能把已撤回状态悄悄复活。

## 6. 所有入口的交互矩阵

| 入口 | 首写推荐策略/必须验证 |
| --- | --- |
| Correct/type/amount | 任一活动成员阻断；先撤回，不能只更正代表或被抑制的一方 |
| Refund/反向退款关系 | 任意成员及历史退款关系需检查；首写禁止已有相关退款、关联后新增退款先撤回。不能只复用active refundTotal |
| Annotate/category/note | D5未明确允许前全部阻断；分类也影响正式投影，不把Version>1一概当金融更正或一概忽略 |
| ImportUndo | 先读取批次全部影响集合；若涉及活动成员/组/证据关系，首写整操作冲突，零表变化，不部分撤销其他行再报错 |
| RestoreImport | 同样先全量预检，不能因恢复一个成员破坏组、复活别的操作或改变决策依据 |
| Native/standard/legacy Commit | 先定义新增、重复链接、source evidence刷新对活动组的影响；首写遇到涉及组的变更整批冲突并保持原预览/账务，不把新证据默认为同事件。无新增证据/成员变化的严格已完成重放可按原幂等合同返回历史结果，不能借重放恢复组或扩充证据 |
| 手工新增相似交易 | 若是合法独立消费可正常新增，保持独立贡献；不靠tuple自动并组。相似不是关系写入 |
| 新source config/import binding | 同bytes仍可能对应同import，未来须独立关联表；不改旧hash/identity/Source。增加配置不替代原证据或角色校验 |
| 批量操作/未来后台执行器 | 必须复用同一guard和有效投影，不能绕前台restriction；未接入前不启用 |

不能以换key或拆成单条请求绕开上述guard。整批拒绝的范围和原因必须在预览中提前说明；它是保守首写建议，非现有main行为。

## 8. 可独立推进的切片与退出条件

- **本片：** 代码事实、选项/D门槛、读写交互矩阵及未来合成验收。文档审查与链接/基线核对，不等于财务或GUI功能验收。
- **S3a：** 明确D1–D8，协调源冻结、迁移及兼容策略；确认产品选择后提交类型化模型与迁移/备份/旧版本拒绝测试，写端点仍不开放。
- **S3b：** 实现统一effective transactions/postings和所有读消费者；无关联基线不变，暂无用户创建关系通道。
- **S3c：** 一起实现preview/confirm/withdraw与所有旧写/导入guard、完整幂等/并发测试；不得只上线confirm或只改Dashboard。
- **S3d：** 正常双端受控合成账本执行完整矩阵，真实旧迁移/来源证据单列；未验项保留，不标全M11完成。

实施顺序须显式解决未合并依赖。PR17来源冻结的保护不能假定在main已存在；PR18只读合同不能承担未来financial write。没有原始样本、正常登录/图形能力或迁移顺序时继续准备不依赖它们的工作，不读取真实账单/DB、不绕过鉴权、不自动合并或部署。
