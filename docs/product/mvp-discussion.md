# Monee MVP 产品讨论稿

状态：完整 MVP 仍在逐步实施。更新：2026-09-14。

当前已交付 Web / Mac 共用 Go + SQLite 的基础链路：标准 CSV 导入、手动收入/支出、去重预览、月度统计和持久化。目录/邮件、专有格式、退款/还款、主动分析、备份恢复仍是后续范围，详见[实现记录](../architecture/local-data-flow.md)。

品牌名称：**Monee**。Slogan：**Know Your Money. Own Your Future.** Logo 原图与使用说明见[品牌说明](../brand.md)。

## 已确认的方向

- 最终支持 iOS、Android、Mac App 和浏览器 Web。
- 第一版自己使用，优先 Web / Mac，手机端随后补齐。
- 客户端确定采用 KMP + Compose Multiplatform，共享 Web/Mac 界面与客户端逻辑，并为 iOS/Android 扩展；服务端使用 Golang。
- 第一版本机存储，Web/Mac 共用本地账本；后续同步到云端数据库，设计时考虑数据兼容性。
- 从支付宝、微信、银行卡、京东白条的历史账单建立数据，再做统计、分析、展示。
- 首批银行适配目标：招商银行、农业银行、上海银行、工商银行；具体卡种及账单格式待核实。
- 用户希望打破貔貅所依赖的日常人工观测习惯。核心是自动归集与主动分析，手动记账只作补漏；付款后自动记账作为待验证的增强能力。
- 获取账单尽量自动接收邮件附件或指定文件夹中的文件，必要时补充手动导出；付款实时捕获不是第一版前提。

## 产品定位建议

把分散的账单变成一个可信、可追溯、持续更新的个人账本，主动解释值得关注的变化，减少每日记录和查看报表的负担。

首个闭环：获取一个月账单 → 自动识别来源、规范化、检查重复并分类 → 只集中处理影响账本正确性的疑问 → 自动生成月度解释与可追溯明细。首次导入确认来源和预览口径；经过验证的来源可配置后续自动入账，减少反复确认。

首屏先回答三个问题：本月最值得注意的变化是什么，变化由哪些交易造成，现在是否有需要处理的事项。详细收支和分类图表可继续下钻。报表应展示已导入的来源、覆盖时段和待确认笔数；缺失数据不能被呈现成完整财务状况。

产品验收除了金额正确，还看人工处理比例、每次补充账单后的操作次数，以及解释能否直接回答问题；不以连续打卡或每日打开 App 为成功标准。

## 建议的第一版页面

| 页面 | 必须完成的任务 |
| --- | --- |
| 总览/洞察 | 优先展示变化原因、集中待处理事项和数据完整度，再提供月收入、净支出、分类排行；可点进组成数字的交易 |
| 交易 | 搜索、时间/分类/账户/来源筛选，查看原始记录，新增、编辑、撤销、拆分分类 |
| 导入 | 选择来源和账户，解析预览，展示成功/重复/待确认/失败笔数和原因，确认入账及撤销批次 |
| 待确认 | 处理疑似重复、账户不明、退款未关联和无法识别的收支类型 |
| 账户 | 现金、银行卡、支付宝余额、微信零钱、信用卡/白条等；设置期初余额和日期，查看余额变动 |
| 设置 | 分类、标签、分类规则、完整备份/恢复、数据导出 |

作为补漏，日常记账覆盖支出、收入、账户间转账、信用账户还款、退款和余额调整。快速记账优先输入金额，再选择分类和账户，默认当前日期；备注和标签可选。用户界面不要求理解会计分录。

### 主动分析的首版范围

| 输出 | 生成依据与行为 |
| --- | --- |
| 月度变化解释 | 在相同来源与可比时段计算类别/商户变化和贡献最大的交易，附计算范围和交易链接 |
| 固定支出变化 | 多期相同商户与周期的交易提示疑似固定支出；涨价、重复或缺失仅提示核实，不假定已订阅或被多扣款 |
| 待处理摘要 | 聚合疑似重复、退款未关联、来源缺失、识别失败；一次处理同类问题并可保存规则 |

首版用确定性计算和文字模板生成解释，保证可复现。未知分类可以进入“未分类”并计入已确认总额，不要求逐笔选择才能使用；金额、账户和重复性存在实质不确定时才阻止正式入账。用户修正后可选择应用于未来同类交易，涉及历史数据批量重算时先展示影响。

建议按新账单到达或完整月度数据更新触发分析，不要求每日主动观察。提醒设置由用户控制；相同未解决问题不反复提醒，数据不足时不生成没有依据的变化结论。

## 统计口径建议

1. 支付渠道与资金账户分开。通过支付宝用银行卡付款，支付宝是渠道，银行卡是资金来源；不能既扣支付宝余额又扣银行卡。
2. 多条原始流水可能描述同一笔真实交易。支付宝消费 100 元和银行卡扣款 100 元，确认关联后只计一笔消费；不能仅按金额和相近时间自动合并。
3. 信用卡、白条先消费后还款。建议消费发生时记录支出及负债，还款本金只减少银行资产和负债，利息/手续费另外计支出。
4. 本人账户互转、提现、充值不计收入和消费。别人转入的钱需要区分收入、退款、借款、报销或其他性质。
5. 保留消费与退款两条事件并关联。默认退款按退款发生日抵减该期支出，展示消费毛额、退款和净额；跨月退款不无声改写旧月报表。
6. 余额调整不作为收入或消费。没有期初余额和完整流水时，不把推算值当作已核实资产或净资产。
7. “不计收支”不是“删除流水”。它仍可能改变账户余额，需保留业务语义。
8. 首版建议人民币单币种；未知币种或其他币种不能静默按人民币处理。

## 账单接入顺序与边界

| 来源 | 首版建议 | 需要验证的输入 |
| --- | --- | --- |
| 支付宝 | 原始导出文件适配器，保留交易号与支付方式 | 用户实际导出文件的表头、编码、状态、退款格式 |
| 微信 | 原始导出文件适配器，支持与其他来源对账 | 用户实际导出文件的类型、表头、支付方式和订单标识 |
| 银行卡 | 招商、农业、上海银行、工商银行分别适配，同时提供通用表格列映射 | 各行储蓄卡/信用卡分布、实际账单格式和记账日期含义 |
| 京东白条 | 单独识别消费、退款、还款本金、手续费 | 实际可取得的明细格式；官方帮助已确认可查询明细，尚未验证可直接导出的格式 |

四类来源都属于目标范围。首条可运行链路可从支付宝/微信和通用模板开始；银行与白条的原生适配必须使用真实格式的脱敏样本验证后才称为支持。通用模板是可用的补充入口，不能替代对原生文件支持状态的说明。

CSV/XLSX 优先。PDF、截图识别作为后续适配路径，识别结果先预览再入账。不得根据猜测填补未知金额、币种、时间或账户。个人账单接入与商户收款对账接口不是同一种授权能力。

获取账单与处理账单分开评估。用户已选择尽量自动接收邮件附件或指定文件夹中的账单，必要时补导出。当前先以手选标准 CSV 验证数据处理链路；自动接收阶段先做指定文件夹，邮件附件入口随后复用相同导入链路；邮件服务商和身份验证方式在接入前确认。指定文件夹仅处理用户配置的来源，邮件接入需要独立配置授权与适配，不假定四家银行都支持同一种推送或导出。第一版不会因处理流程自动化就宣称已实现自动获取所有流水。

本地接收依赖电脑开机且 Monee 服务运行。休眠/退出期间不宣称仍在接收；下次启动补扫文件并增量补拉邮件，展示最后成功检查时间和数据覆盖范围。损坏或加密的附件进入待处理，并允许重新解析，不因一个文件失败而停止整个来源。

## 自动记账的产品策略

先支持“捕获信息 → 生成草稿 → 用户确认 → 入账”。草稿不进入正式报表，后续导入正式账单时能关联并补全已有记录。

- Android：验证授权后的通知监听，针对支付通知提取候选交易。没有通知、字段缺失、设备后台限制都可能造成漏记。
- iOS：验证快捷指令/App Intents、分享入口；Apple WWDC26 展示了来自指定 App 的通知触发及关键词筛选。此能力不等于已经验证支付宝/微信可完整自动记账；需核实系统版本、真实通知内容和锁屏执行情况。
- 两端均保留手动确认和定期账单核对，重复通知不产生重复入账。
- 等真实样本证明准确性后，再考虑让用户开启高置信规则自动入账，并保留记录、撤销和核对能力。

## 实施阶段建议

1. 账本核心与 Web 闭环：账户、指定文件夹自动归集、重复检查、分类规则、集中待确认、月度解释与明细下钻、备份恢复，以及手动补漏入口。
2. 邮件与账单格式扩充并交付 Mac：接入实际使用的邮箱，复用 KMP 共享 UI，补齐常用银行与白条适配，验证文件选择、存储、应用退出重启后的数据一致性。
3. 移动端：复用接口、规则和可复用 UI，优化单手记账、分享导入和平台集成。
4. 自动化捕获：在实际 iOS/Android 设备验证，再接入待确认流程。

首版验收要看行为：重复导入不增加支出；支付宝与银行匹配后只计一次；消费 100 元退款 20 元后净支出 80 元；白条还本不重复计支出；撤销导入不破坏手工记账；每张报表能追溯到交易及来源。
